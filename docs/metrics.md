# Metrics definitions

Определения зафиксированы на день 6, до написания витрин. Изменение
определения метрики — отдельный коммит с объяснением причины.

## Выручка

Выручка считается раздельно для товаров и доставки — это маркетплейс,
доставку получает перевозчик, а не платформа.

| Метрика | Статусы заказа | Смысл |
|---|---|---|
| revenue_delivered | delivered | подтверждённая выручка, не меняется задним числом |
| revenue_pipeline | все кроме canceled, unavailable | включая заказы в пути, может уменьшаться при отменах |

**Почему не одна метрика.** Заказы в статусе shipped/processing составляют
~2% от объёма delivered, но их часть впоследствии отменяется. Смешение
в одну метрику даёт эффект "цифра закрытого периода меняется задним числом" -
неприемлемо для отчётности перед руководством.

revenue_delivered = sum(price) WHERE order_status = 'delivered'
revenue_freight_delivered = sum(freight) WHERE order_status = 'delivered'

## Период отнесения

Заказ относится к периоду по дате purchased_at (дата оформления),
не по дате доставки или оплаты.

Обоснование: соответствует моменту решения клиента, корректно стыкуется
с датой рекламных расходов в marketing_spend.

Ограничение: финансовая отчётность может считать по дате оплаты/отгрузки.
При расхождении с фин. отчётами - первое, что нужно проверить.

## Средний чек (AOV)

AOV = revenue_delivered / count(DISTINCT order_id WHERE status = 'delivered')

Знаменатель - число ЗАКАЗОВ, не позиций и не клиентов.
- на позицию было бы "средняя цена товара"
- на клиента было бы ARPU

## Категории товаров

610 товаров (1 603 позиции в заказах) не имеют категории.
Не исключаются из витрин - агрегируются в группу 'undefined'.
Молчаливое исключение занижает выручку без объяснения причины.

## Клиенты

Подсчёт клиентов, retention, LTV, RFM - только по customer_unique_id.
customer_id из источника - это клиент в рамках одного заказа,
использование даёт retention = 0%. См. known_defects.md.
